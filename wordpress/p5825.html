JavaFX の TextArea で漢字文字を使用する際のパフォーマンス問題のワークアラウンド

Posted on 2018年7月24日

この記事では TextAreaの2つのパフォーマンス問題 [JDK-8090110, JDK-8089418] の回避方法を紹介します。 ここで紹介する方法を使うことによって、TextAreaの扱えるデータサイズが10 倍以上増えます。漢字だけでなく、アルファベット文字においてもパフォーマンスが改善されます。

ここで紹介するコードは一時的な解決です。将来の JavaFX のバージョンでは動作しないかもしれないので注意してください。

問題

「Very bad TextArea of performance in a language environment that uses the Chinese character (KANJI)」 https://bugs.openjdk.java.net/browse/JDK-8090110

この問題は私が2014年に報告していたもので、報告後にワークアラウンドを見つけました。 TextArea は100KBの文字数で明らかに実用的なレスポンス速度ではなくなります。 このパフォーマンス問題は大規模なテキストデータの編集に使えないことを意味しており UI 設計の制約となります。

次も同時期に私が報告したTextArea のパフォーマンス問題です。

When the TextArea control is to increase the font size Operation response is slow https://bugs.openjdk.java.net/browse/JDK-8089418

フォントサイズ上げた場合にTextAreaのパフォーマンスが劣化する現象で、 実際にはこのような利用シーンはレアケースですが、私がTextArea のパフォーマンス問題のワークアラウンドを見つけるヒントになっています。

環境

このパフォーマンス問題は初期のリリースからあり漢字を扱う言語圏、従って日本、中国、台湾が影響範囲になります。

解決

２つのテストコードから TextArea のパフォーマンスが劣化する要因には以下のものがあることが分かります。

  • 漢字文字(おそらく漢字に限定せずパスの多い文字)のテキストデータ

  • データサイズ

  • フォントサイズ

  • (折り返し設定)

テストコードで折り返し設定をオフにしても問題が再現できるので、必要条件ではないと分かります。ここでは無視していいでしょう。

フォントサイズが大きくなると表示する文字が少なくなりレンダリングする必要のある文字数は少なくなりますが、 逆にパフォーマンスが劣化するので想定する動作と異なります。 この現象から表示範囲外の処理負荷が無視できない程に高くなっていると推測できます。

TextAreaの実装にはクリップ処理がないので、クリップ処理を追加します。

次のテストコードでUSE_WORKAROUND=true を設定するとパフォーマンスが改善されていることを確認できます。

このワークアラウンドを使用することで漢字だけのテキストデータでは実用的な限界は1MB程度になります。 日本語の場合は、平仮名やカタカナを含むので、あと数倍は伸びるでしょう。 クリッピング処理が適切に行われることでアルファベット文字においても操作レスポンスが改善されます。 従って、このワークアラウンドは漢字を使わない言語圏でも有効です。

現在の TextArea の設計ではこれ以上の大幅な改善は見込めないと思います。 1MB以上のテキストデータサイズを扱いたい場合は、異なる設計による別のTextArea(Text Editor Engineというべき)実装が必要になるでしょう。

この問題は2014年から解決していませんが、私がこの記事で示したとおり大幅なコード変更なしに修正できます。 JavaFX の開発チームはミスリードしておりグラフィックスチームにアサインしていますが、 この判断が間違いであり、TextArea の実装に問題があることを、このワークアラウンドは実証しています。 この記事を読んだ人の中で、JavaFX チームとつながりのある方は教えてあげましょう。 そうしなければ、この問題は残り続けるでしょう。
